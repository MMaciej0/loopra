## Module Convention

Every feature module follows the same internal structure:

```
modules/<name>/
  index.ts        # Registers Fastify plugin, mounts routes on a prefix
  routes.ts       # Route definitions (method, url, schema, handler)
  schema.ts       # Zod schemas for request body, params, query, response
  services/       # Business logic — pure functions, no Fastify types
    <action>.ts   # One file per service action (e.g. registerUser.ts, loginUser.ts)
    cookies.ts    # Shared cookie helpers (setAuthCookies, clearAuthCookies)
```

Services receive `db` and `redis` as parameters, making them independently testable.

## Authentication Flow

Both tokens are delivered via **httpOnly cookies only** — no `Authorization` headers, no tokens in response bodies. JS never has access to either token.

### Email verification gate

Registration and login are allowed before email verification so users can see the product value quickly. Verification gates participation, not discovery.

Unverified authenticated users can:

- search and browse rides
- view ride details
- view and edit their own basic profile
- resend the verification email

Unverified authenticated users cannot:

- create rides
- join/request to join rides
- write in ride chat
- create groups/clubs
- upload routes/GPX
- send direct messages

Protected write/participation routes should use a separate `requireVerifiedUser` guard after the normal auth guard. If the user is authenticated but `email_verified_at` is null, return `403 EMAIL_NOT_VERIFIED`.

Example response:

```json
{
  "type": "EMAIL_NOT_VERIFIED",
  "message": "Verify your email to continue."
}
```

### Cookies

| Cookie | Value | httpOnly | Path | Max-Age |
|--------|-------|----------|------|---------|
| `accessToken` | signed JWT | ✓ | `/` | 15 min |
| `refreshToken` | `{familyUuid}.{rawToken}` | ✓ | `/auth` | 30 days |

Restricting `refreshToken` to `/auth` ensures the browser only sends it to auth endpoints (refresh, logout), not to the rest of the API.

### Token families

Each login on each device creates an independent **token family** — a UUID that identifies the session. This enables:

- Multiple devices logged in simultaneously (browser + mobile = two families)
- Per-device logout without affecting other sessions
- **Refresh token reuse detection**: if a rotated (already-used) token is presented again, **all families for that user** are invalidated immediately — logging out all devices (theft response)

The `familyUuid` is not secret — it's just a session identifier. The `rawToken` is the secret. Both travel together in the `refreshToken` cookie as `{familyUuid}.{rawToken}`.

### Redis structure

```
family:{familyUuid}           →  { userId, refreshTokenHash }    TTL: 30d
user:families:{userId}        →  Set[ familyUuid, ... ]          (no TTL — cleaned on logout)
email-verification:{tokenHash} → userId                          TTL: 24h
```

- **Access token**: not stored server-side. JWT is self-contained (`{ sub: userId }`), verified by signature on every request — zero DB or Redis lookups.
- **Refresh token**: stored in Redis only, no DB table.
- **Email verification token**: raw token is sent only by email; Redis stores only a hash for single-use confirmation.

### Flows

**Register**
1. `familyUuid = uuid()`
2. `rawToken = crypto.randomBytes(32).toString('hex')`
3. `tokenHash = sha256(rawToken)`
4. `redis.set(family:{familyUuid}, { userId, tokenHash }, EX 2592000)`
5. `redis.sadd(user:families:{userId}, familyUuid)`
6. Sign access JWT (`{ sub: userId }`, 15 min expiry)
7. Set both httpOnly cookies; `refreshToken` value = `{familyUuid}.{rawToken}`
8. Create a single-use email verification token, store only its hash in Redis with a 24h TTL, and send the verification link by email.
9. Return `{ user: { id, email, email_verified_at: null } }` — no tokens in body

**Login**
1. Validate email + password.
2. Create token family using the same cookie/session flow as register.
3. Return `{ user: { id, email, email_verified_at } }`.
4. Do not block login for unverified accounts; block participation routes instead.

**Authenticated request** (any protected route)
1. `@fastify/jwt` reads `accessToken` cookie, verifies signature
2. Populates `request.user = { sub: userId }`
3. Zero DB or Redis lookups

**Verified participation request** (create/join/chat/etc.)
1. Run the normal auth guard.
2. Load the current user from DB.
3. If `email_verified_at` is null, return `403 EMAIL_NOT_VERIFIED`.
4. Otherwise continue to the handler.

**Verify email** (`GET /auth/verify-email?token=...`)
1. Hash the raw token from the URL.
2. Look up the hash in Redis.
3. If missing or expired, return `401 INVALID_TOKEN`.
4. Set `users.email_verified_at = now()`.
5. Delete the token so it cannot be reused.
6. Redirect to the frontend email-verified state or return success for API clients.

**Resend verification** (`POST /auth/resend-verification`)
1. Require authentication.
2. Load the current user.
3. If already verified, return success without sending a new email.
4. Create a new single-use token, store only its hash in Redis with a 24h TTL, and send the verification link.
5. Rate-limit this endpoint to prevent email abuse.

**Refresh** (`POST /auth/refresh`)
1. Parse `refreshToken` cookie → `[familyUuid, rawToken]`
2. `tokenHash = sha256(rawToken)`
3. `family = redis.get(family:{familyUuid})`
4. If `family` not found → expired or already invalidated → 401
5. If `family.tokenHash !== tokenHash` → **reuse detected** (possible theft):
   - `familyIds = redis.smembers(user:families:{userId})`
   - `redis.del(...familyIds.map(id => family:${id}))` — all families nuked
   - `redis.del(user:families:{userId})`
   - Clear both cookies
   - Return 401 — force re-login on all devices
6. Valid — rotate:
   - Generate new `rawToken` + `tokenHash`
   - `redis.set(family:{familyUuid}, { userId, newTokenHash }, EX 2592000)` — same familyUuid
   - Issue new access JWT
   - Set both cookies with new values

**Logout** (`DELETE /auth/logout`) — this device only
1. Parse `refreshToken` cookie → `familyUuid`
2. `redis.del(family:{familyUuid})`
3. `redis.srem(user:families:{userId}, familyUuid)`
4. Clear both cookies

**Logout all devices** (future — `POST /auth/logout-all`)
Same as reuse detection: delete all families + the set, clear cookies. The internal `deleteAllFamilies(redis, userId)` helper already implements this — the endpoint just needs a route + auth check.

**Google OAuth** (`GET /auth/google` → `GET /auth/google/callback`)

OAuth is an alternative identity verification path. Once the user's identity is confirmed via Google, the session is created using the same token family system — the JWT, refresh rotation, and Redis structures are identical to password login.

1. `GET /auth/google` — server redirects browser to Google's consent screen:
   ```
   https://accounts.google.com/o/oauth2/v2/auth
     ?client_id=GOOGLE_CLIENT_ID
     &redirect_uri=GOOGLE_CALLBACK_URL
     &response_type=code
     &scope=openid email profile
     &state=<random_csrf_token>        ← stored in a short-lived cookie
   ```
2. User grants consent on Google's UI.
3. Google redirects to `GET /auth/google/callback?code=AUTH_CODE&state=<token>`.
4. Server validates `state` matches the cookie (CSRF check).
5. Server POSTs to Google's token endpoint with `code` + `client_secret` → receives `access_token` + `id_token`.
6. Server calls `https://www.googleapis.com/oauth2/v3/userinfo` with the access token → receives `{ sub, email, email_verified, name, picture }`.
7. `findOrCreateOAuthUser(db, provider="google", providerUserId=sub, email, name, picture)`:
   - Find `oauth_accounts` by `(provider, providerUserId)` → user exists → proceed to step 8
   - Else find `users` by `email` → link new `oauth_accounts` row to existing user → proceed to step 8
   - Else create new `users` row (`password_hash = null`) + new `oauth_accounts` row
   - If Google returns `email_verified = true`, set `email_verified_at` for that user.
8. `createTokenFamily(redis, userId)` — same as password login from here
9. Sign access JWT, set both httpOnly cookies.
10. `302` redirect to `FRONTEND_URL` (e.g. `/dashboard`).

**Why `sub`, not `email`?** Google's `sub` is a permanent, immutable user ID. Email can be changed or transferred. Always identify OAuth users by `provider_user_id = sub`.

### Plugin setup

```ts
// plugins/auth.ts — JWT + cookie auth
fastify.register(jwt, {
  secret: config.JWT_ACCESS_SECRET,
  cookie: { cookieName: 'accessToken', signed: false },
})
fastify.register(cookie)

fastify.decorate('authenticate', async (request, reply) => {
  await request.jwtVerify() // reads accessToken cookie automatically
})
```

```ts
// plugins/oauth.ts — Google OAuth via @fastify/oauth2
fastify.register(oauth2, {
  name: 'googleOAuth2',
  scope: ['openid', 'email', 'profile'],
  credentials: {
    client: { id: config.GOOGLE_CLIENT_ID, secret: config.GOOGLE_CLIENT_SECRET },
    auth: oauth2.GOOGLE_CONFIGURATION,
  },
  startRedirectPath: '/auth/google',          // GET /auth/google → redirect to Google
  callbackUri: config.GOOGLE_CALLBACK_URL,    // Google redirects back here with ?code=
})
// Exposes: fastify.googleOAuth2.getAccessTokenFromAuthorizationCodeFlow(request)
// state CSRF token is handled automatically by the plugin
```

**Note:** `userinfo()` from the plugin only works with the `discovery` option. We use static config, so after token exchange we call Google's userinfo endpoint directly:
```ts
const resp = await fetch('https://www.googleapis.com/oauth2/v3/userinfo', {
  headers: { Authorization: `Bearer ${token.access_token.token}` },
})
const { sub, email, name, picture } = await resp.json()
```

### Required env vars for OAuth

| Variable | Description |
|----------|-------------|
| `GOOGLE_CLIENT_ID` | From Google Cloud Console → APIs & Services → Credentials |
| `GOOGLE_CLIENT_SECRET` | Same as above — **never expose to browser** |
| `GOOGLE_CALLBACK_URL` | Must match exactly what's registered in Google Console — e.g. `http://localhost:3000/auth/google/callback` |
| `FRONTEND_URL` | Redirect destination after successful OAuth — e.g. `http://localhost:3001` |

### Mobile note

React Native (Expo) does not have an automatic cookie jar — httpOnly cookies from `Set-Cookie` will not be attached automatically. Mobile auth strategy will be decided when the mobile app is built (Phase 3). The service layer is transport-agnostic and will not change.

## Geospatial Queries

All location-based queries use PostGIS `ST_DWithin` with geography type for accurate distance in meters.

Example — nearby rides within 50km:
```sql
WHERE ST_DWithin(
  rides.start_location::geography,
  ST_SetSRID(ST_MakePoint($lng, $lat), 4326)::geography,
  50000  -- meters
)
ORDER BY rides.start_location <-> ST_SetSRID(ST_MakePoint($lng, $lat), 4326)
```

## Pagination

All list endpoints use **cursor-based pagination** (not offset) for consistent results on frequently-updated datasets.

Request: `?cursor=<opaque_string>&limit=20`
Response: `{ data: [...], nextCursor: "<string>" | null }`
